# The six "bench step" items: what research changed, and what is now in the design

These six issues were each classified as "the mechanism is implemented, the number needs
hardware". Research changed that for most of them — two of the three "no data available" claims
turned out to be wrong — and the rest are now instrumented so the bench step is a readout rather
than an experiment.

## #5 PA thermal — the datasheet has the number that was assumed unavailable

The issue said Qorvo's Rth was NDA-gated. It is in the brief, in the thermal section:

```
Thermal Resistance (theta_JC)  2.60 degC/W                    <- QPA1010, the chosen device
    T_BASE -40 to +85 degC, VD = 24 V, IDQ = 600 mA
    quiescent P_DISS = 24 x 0.6 = 14.4 W
    driven  P_DISS = 39.8 - 15 = 24.8 W   (P_DC 15 W / 37.7 % PAE, minus the RF that leaves)
```

The model is one multiplication above the case, so a measured case temperature converts to a channel
temperature directly. **For this device driven is the safe planning number, not quiescent** — the
opposite of the QPA2962, whose quiescent dissipation (36.96 W) exceeded its driven figure (35.5 W).
`PA_THERMAL.h` derives `PA_PDISS_PLAN_W` as the larger of the two rather than naming one, so the
direction cannot be got wrong by habit.

**What that says about the design.** The channel limit (200 °C design) is reached at a case
temperature of **135 °C**, and the datasheet's own T_BASE maximum of 85 °C binds long before it. At
the firmware's 75 °C sensor limit the channel sits at `75 + 2.60 x 24.8 = 139 °C`, well inside.
`test_pa_thermal.c` checks the model against the datasheet, so the numbers cannot drift.

**A real bug it exposed.** The PA over-temperature check read:

```c
int Max_Temp = 25;      // ...while the comment beside it said ">75 C"
```

25 °C would trip constantly — or, since no board populates the sensors, never. It now reads 75,
which the physics supports (75 + 2.60 x 24.8 = 139 °C channel, inside the limit).

**The remaining gap is hardware, and it is specific:** the firmware declares eight sensors
(`Temperature_1..8`) and **no board has one**. That is what this issue needs: eight case
thermistors (one per PA pair, matching the firmware's eight variables) and a decision on how they
reach the MCU, because the harness has no spare position. That decision is the owner's, not mine
to guess.

## #7 harmonic filtering — the level is characterized, so it can be read rather than measured

The brief carries a harmonics section: 2nd and 3rd harmonic versus P_OUT versus temperature,
versus V_D and versus I_DQ. So the required filter order follows from plots that already exist —
the numbers are in the PDF's graphs rather than in its text layer, so they have to be read by eye,
but that is a different task from "build the board and measure it".

The requirement stands as written (≥ 35 dB at 21.0 and 31.5 GHz), and the interface is
unchanged: one inline SMA-to-SMA filter per element between `J2` and the antenna, no board
change. With the PA's own harmonic level read off the plots, the order is a calculation rather
than a bench campaign.

## #19 OCXO inrush — the vendor and the datasheet are located

The part is **ECS Inc. ECOC-2522-100.000-3HC**, and its datasheet is at
`ecsxtal.com/store/pdf/ECOC-2522.pdf`. The claim that no vendor data was reachable is no longer
true. The parameter table does not survive text extraction (the PDF's tables are image-based), so
the steady and warm-up currents have to be read from the document rather than parsed.

The design-side answer, computed: the `+3V3_XO` rail carries 88 µF of added bulk on a
TPS7A8300 rated 3 A. Inrush into that bulk is bounded by the regulator's current limit — roughly
`3 A / 88 µF = 34 V/ms`, so the rail reaches 3.3 V in about 0.1 ms. What the bulk *cannot* cover
is a sustained warm-up surge: at 500 mA for 1 ms the droop is `I·t/C = 5.7 V`. So the honest
statement is that the inrush is bounded but the OCXO's warm-up profile decides whether the bulk
is adequate — which is exactly the bench capture this issue asks for, now with a located source
and a computed requirement rather than a guess.

## #20 the supply order — verifiable in the design, once the rails can be sensed

The order is documented, cited and locked by `test_adar_power_order.c`, so what remains is
observing it on real hardware. The ADAR rails are generated by TPS562208 bucks (`U6`, `U7`,
`U13`), which have **no PG pin**, so the existing rail-good monitoring cannot see them.

Making the order self-verifying needs rail sensing: two free MCU ADC channels with dividers on
`+3V3_ADAR12` and `-5V0_ADAR12`, sampled during the sequence. That turns the scope capture into a
telemetry field. It is specified here rather than implemented because it adds two nets and a
wiring decision, and because the firmware already asserts the order that the test protects.

## #13 dropped strobe — now a self-test, not an assumption

`StrobeAck_SelfTest_*` raises a strobe at bring-up and watches for the acknowledgement, retrying
three times (a chirp already in flight will legitimately drop one). The result appears in
telemetry as `StrobeAckPath`. The *functional* case — a strobe dropped mid-chirp — remains what
the miss counter is for, and a bench check can force it by issuing two strobes back to back.

## #14 the ADC answers — now a self-test with known values

The single hopeful read of `0x2A` is replaced by a read of two registers whose defaults the
datasheet states: `0x00 CHIP_PORT_CONFIG = 0x18` and `0x2A OVR_CONFIG = 0x01`. Nothing is
written, so the test is safe at any time, and a dead bus shows up as all-zero or all-one rather
than as a plausible-looking value. Telemetry reports both readings and the verdict as
`ADC_SPI` / `ADC_OVR`.
